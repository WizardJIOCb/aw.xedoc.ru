# Развёртывание AW XEDOC

Целевой VPS: **82.146.42.213**, SSH alias `myserver`. Адрес 62.109.9.134 из
предыдущего сообщения больше не является выбранной целью. Перед публичным
запуском A-запись `aw.xedoc.ru` должна указывать на 82.146.42.213; старую AAAA
запись нужно проверить отдельно, чтобы IPv6 не отправлял браузеры на другой VPS.

В текущей проверке цели уже найдены Node.js 24.12, npm 11.6, Nginx и certbot;
порт 3188 свободен. Установщик всё равно перепроверяет текущий runtime,
конфигурацию Nginx и владельца порта перед переключением.

## Каталоги и границы

Каждый релиз находится в `/var/www/aw.xedoc.ru/releases/<полный Git SHA>`.
`/var/www/aw.xedoc.ru/current` — атомарно заменяемая ссылка на активный релиз.
Исходники, зависимости и клиент после сборки принадлежат root; системный
пользователь `aw-game` запускает Node.js и пишет только игровые сохранения.

Состояние игроков хранится в `/var/lib/aw-xedoc/state.json`, отдельно от релизов.
Его не нужно копировать из локального `.runtime`, класть в Git или удалять при
обновлении. Парольные bcrypt-хеши и хеши сессий находятся в этом JSON; резервные
копии доступны только root в `/var/backups/aw-xedoc/`.

В `release.env` нет секретов: production, bind/port, HTTPS Origin, путь состояния
и точный `SOURCE_COMMIT`. Проверка `/api/health` сравнивает эту версию с нужным SHA.
Наличие SHA в health доказывает конфигурацию запущенного релиза; соответствие
загруженных файлов Git-коммиту дополнительно обеспечивается архивом из Git.

## Подготовка и установка

Исходный архив создаётся из **закоммиченного** состояния репозитория. Например,
на Linux/macOS или в Git Bash:

```bash
commit=$(git rev-parse HEAD)
git archive --format=tar.gz --output="aw-$commit.tar.gz" "$commit"
scp "aw-$commit.tar.gz" myserver:/tmp/
```

На VPS, после проверки ожидаемого полного SHA:

```bash
commit=<полный-SHA-из-git-rev-parse-HEAD>
install -d -m 0755 "/var/www/aw.xedoc.ru/releases/$commit"
tar -xzf "/tmp/aw-$commit.tar.gz" -C "/var/www/aw.xedoc.ru/releases/$commit"
bash "/var/www/aw.xedoc.ru/releases/$commit/deploy/install-release.sh" "/var/www/aw.xedoc.ru/releases/$commit" "$commit"
```

Установщик требует root и Node.js ≥22 в `/usr` или `/opt`: приватный runtime в
`/root/.nvm` несовместим с `ProtectHome`. Он создаёт пользователя `aw-game`,
выполняет `npm ci --include=dev`, тесты и сборку от его имени. `tsx` нужен в
production, поэтому dev dependencies сохраняются. Установка проверяет, что
release path действительно находится внутри указанного каталога и соответствует
SHA; symlink escape отклоняется.

Прежде чем менять работающий релиз, установщик выполняет проверки и сборку.
Порт, занятый чужим процессом, он не освобождает. Nginx-сайты других проектов
сохраняются. Первый AW HTTP-сайт создаётся из `deploy/nginx.conf`; последующие
релизы сохраняют этот файл, включая правки HTTPS от certbot. При другом уже
существующем конфиге `aw.xedoc.ru` установщик останавливается для его проверки.

Проверка HTTP через локальный Nginx выполняется с `--resolve`, поэтому установка
работает до смены публичного DNS. После переключения systemd и Nginx должны
показать health именно нужного SHA и вернуть страницу клиента.

## DNS и сертификат

Проверьте записи с нескольких резолверов и доступность порта 80 извне. Пока DNS
указывает на старый VPS, сертификат для этой цели получать нельзя.

```bash
dig +short A aw.xedoc.ru
dig +short AAAA aw.xedoc.ru
curl --fail --show-error http://aw.xedoc.ru/api/health
```

После переноса DNS и проверки HTTP root отдельно запускает:

```bash
certbot --nginx -d aw.xedoc.ru --redirect
nginx -t
systemctl reload nginx
curl --fail --show-error https://aw.xedoc.ru/api/health
certbot renew --dry-run
```

Начальный Nginx-конфиг не содержит путей к ещё не выпущенному сертификату.
Новый публичный игровой аккаунт следует создавать после проверки HTTPS:
сервер выдаёт Secure cookie при корректном `X-Forwarded-Proto: https`.

Завершающая проверка выполняется в браузере на публичном HTTPS: вход,
авторизованный `wss://aw.xedoc.ru/ws`, два игрока, движение, добыча, бой,
крафт, банк и повторный вход с сохранённым прогрессом. Локальный health и
успешная сборка сами по себе эту проверку не заменяют.

## Возврат к предыдущему релизу

Установщик записывает предыдущую ссылку, копию unit и снимок состояния после
остановки старого сервиса. Если новый релиз не проходит health нужного SHA,
он возвращает ссылку и unit, восстанавливает прежний сервис и сохраняет
текущее игровое состояние. Новый HTTP-конфиг удаляется только если он был
создан этим неудачным запуском; прочие сайты не затрагиваются.

Состояние автоматически не откатывается: это сохраняет действия игроков,
успевшие попасть в новый процесс. Если будущая версия изменит формат состояния,
перед релизом понадобится отдельная совместимая миграция и процедура отката.
Сейчас версия JSON-схемы — 1.

Для ручного переключения на уже проверенный существующий релиз остановите
сервис, сделайте приватную копию `/var/lib/aw-xedoc/state.json`, замените `current`
через временную symlink и `mv -T`, затем запустите сервис и сравните health SHA.
Не удаляйте старый релиз или резервную копию, пока результат не проверен.

Логи: `journalctl -u aw-xedoc.service`,
`/var/log/nginx/aw.xedoc.ru.access.log`,
`/var/log/nginx/aw.xedoc.ru.error.log`. Содержимое state JSON и cookie в отчёт
не выводится.
